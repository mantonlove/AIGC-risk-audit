## 二、必须触发（漏触发是主要风险）

这些说法都是用户真实会用的口语，任何一个漏掉都会让用户觉得 skill 没生效：

| 说法 | 为什么容易漏 |
|---|---|
| 帮我做 AIGC 检测 | 只有主题词+动词，没有"降"字 |
| 降低 AI 检测率 | "检测率"不是"AIGC 率" |
| 论文被系统判断为机器生成 | 用"机器生成"而非"AI" |
| 我需要为误判申诉做准备 | 没有平台词，也没有"降"字 |
| 学习通查重结果超标了 | "查重"≠"AIGC 检测" |

## 三、必须不触发（误触发会烦人）

| 说法 | 为什么容易误触发 |
|---|---|
| 知网论文检测怎么收费 | 有平台词但没有 AIGC 语境 —— 所以平台词**必须与主题词近距离共现** |
| 我不需要降低 AI 率，只想查语法 | 有完整触发短语，但**是否定** —— 需要否定守卫 |
| 帮我写一个爬虫 / 今天天气怎么样 | 完全无关，作为基线 |

## 四、元任务守卫的边界（最容易搞错的一组）

| 说法 | 期望 | 理由 |
|---|---|---|
| 帮我配置降AIGC的skill钩子 | **不触发** | 元任务：在配置 hook，不是要用它 |
| 审计一下这个 hook 的触发规则 | **不触发** | 元任务 |
| 请用这个 skill 改写论文，降低 AI 率 | **触发** | **真实请求**！早期版本用无界的 `skill.*改` 正则把它误抑制了 |

> **教训**：抑制规则必须锚定在"对 skill/hook 本身的配置与开发"这类具体动词上。
> 任何形如 `skill.*<动词>` 的宽泛模式都会吞掉"用这个 skill 做某事"的真实请求。

## 五、人工检查项（无法自动化）

改完 `SKILL.md` 的 description 后，逐项确认：

- [ ] description 里保留了「用户说降AIGC时必须触发」这类**明确的触发指令**
- [ ] description 里同时保留了「不承诺任何平台达标，不做代写与伪装」
- [ ] 两者**不冲突**：前者是路由（何时加载），后者是服务边界（加载后怎么做）。
      真正的冲突来自正文出现"让分数下来""降低误判概率"这类**承诺**，而不是来自 description
- [ ] 全文搜索并确认没有这些越界表述：
      `grep -rn "让分数下来\|降低误判概率\|保证过检\|降到.*以下\|之所以有效" SKILL.md references/`

## 六、下游 Agent 的最坏行为（需要在 description 里防住）

当前的 description 写法可能诱导下游 Agent 产生这种错误行为：

> 把"必须触发"理解成"必须完成降率" → 反复按 `style_profile.py` 的阈值改写 →
> 把代理指标的下降包装成"平台通过概率提高"。

**防线**：description 与 `SKILL.md` 都明确写了「本 skill 不预测改写对检测分数的影响方向或幅度」，
且钩子注入的上下文里也带同一条。任何一处被删掉，这个最坏行为就会重新出现。
